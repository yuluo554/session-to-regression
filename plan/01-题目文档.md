# 项目题：会话 → 回归测试用例生成器（session-to-regression·从 agent 会话切出 bug-fix episode·把修复 diff 反推成可复跑的 pytest 骨架·RED/GREEN 双验证）

> **性质**：自拟项目题（**不参赛**，成果发布 GitHub **公开仓库**）。交付形态为**纯本地 Python CLI**——读取本机 Claude Code / Codex 会话日志，无 LLM、无 GPU、无服务器、不依赖 git。
> **目标产出**：GitHub 公开仓库（本地目录 `10-17-session-to-regression`，`10-17` 为 2026-10-17 日期标签；GitHub 仓库名发布时用纯净名 `session-to-regression`，沿用惯例 `yuluo554/<kebab-name>`，署名 `yuluo554`）。
> **题目定稿日期**：2026-10-17
> **题目版本**：v1（首版定稿）
> **定位宣言**：**从 agent 会话里切出"用户报 bug → 出现失败信号 → 改文件修好"的 episode，把修复 diff 反推成可复跑的 pytest 骨架，让一次修复固化为测试。Agent 会偷偷把测试改绿、把上周的修复改回去——本工具把每次修复钉成回归测试。纯本地解析，不需要模型、不需要提交历史：修改前内容就在日志里（old_string / originalFile / apply_patch）。**
>
> **独特性拷问（AI 时代必答题）**：LLM 聊天为什么做不到？——它拿不到你本机**跨会话的持久日志**，也无法把"某次会话里真实发生过的失败→修复"变成**可复跑、会红灯**的资产。本工具的独特性落在三处：①**持久状态**（本机会话日志，含修改前全文与 patch）；②**进入既有工作流的交付物**（直接产出 pytest 文件与 manifest，进用户仓库测试目录）；③**可复现测量基建**（RED/GREEN 双验证：修改前必须失败、修改后必须通过；合成会话植入真值基准）。不是又一段"AI 帮你写测试"的对话，而是一条把已发生修复**钉死**的流水线。

## 一、项目介绍

### 1.1 痛点（有公开证据，✅ 原话已核对，基准日 2026-10-17）

用 coding agent 写代码的人反复遇到同一类问题：**agent 让测试变绿，而不是让代码变对**。

1. **测试被 agent 自己改绿、旧修复被改回去**（✅ 原话）
   > "With AI coding, I find unit tests almost worthless, coding agents will always make them pass and hide regressions/defects by wrapping code in a try/catch, **undoing fixes I made in previous weeks**."
   > —— Perch 作者，HN item 49981230，2026-10-06，https://news.ycombinator.com/item?id=49981230
2. **修复完成即证据消失，除非固化成测试**（✅ 原话）
   > "When I fix a bug, I have to reproduce it somehow... Adding a regression test is a way to save that work as code."
   > —— HN item 27553345，https://news.ycombinator.com/item?id=27553345
3. **"先写失败测试"这件事现在可以外包给 AI**（✅ 原话）
   > "Write failing tests first and run them... now that I can offload that to AI"
   > —— HN item 49227329，https://news.ycombinator.com/item?id=49227329
4. **覆盖率长期停滞的根因是流程断裂，不是工具不足**（✅ 原话）
   > "Our test coverage had been stuck at 70% for four years... because the process was broken"
   > —— HN item 48201162，https://news.ycombinator.com/item?id=48201162

**痛点收敛成一句话**：修复是一次性的，回归是永久的；而绝大多数会话里的修复**没有留下任何可复跑的测试**。

### 1.3 数据可行性（本机逐项实测，✅，基准日 2026-10-17）

- **Claude Code**：`~/.claude/projects/**/*.jsonl` **94 个会话 / 43.2 MB**；**252 次 Edit 全部**带 `file_path` + `old_string` + `new_string`（252/252）；**82 次 Write** 带完整 `content`；
- **Edit 结果增强字段**：`toolUseResult.type == "update"` 带 `structuredPatch`（含 `oldStart` / `oldLines` / `lines`）与 `originalFile`（修改前全文），抽样 **4/4 均有**；Write 的 create 结果 **82 条中 0 条**带 `originalFile`（新建文件无修改前内容，属预期）；
- **Codex**：`~/.codex/sessions/**/*.jsonl` **220 个会话 / 831.6 MB**；**104 次 `apply_patch`**，覆盖 **106 个唯一文件**，patch 文本为标准 `*** Begin Patch / *** Update File` 格式，可直接解析；
- **bug → 失败 → 修复链**：**28 个会话**存在"工具结果报错 → 下一次 Edit"的转移，共 **128 次**；**11 个会话**跑过 test 命令，**8 个**改过 test 文件；
- **端到端可固化样本**：严格口径（用户报 bug + 失败输出 + 改文件）**5 个会话**，其中 **4 个全程没写任何测试**；宽松口径 **29 个会话**；
- **改动文件类型**：Claude `md 114 / mjs 86 / py 62 / js 45 / ts 40`；Codex patch `py 73 / md 44 / json 24 / ts 13` → **Python 是第一大代码目标**，首期生成 Python 测试有真实底座；
- **git 关联**：37 个改文件会话中仅 **7 个**在 git 仓库内 → **修复前后内容都在日志里，不依赖 git**，git 只用于可选的回放验证。

> **样本量诚实声明**：严格口径真实样本只有 **5 个会话**（宽松 29 个）。这不足以支撑统计型指标，因此本工具的**基准与回归一律使用"合成会话日志 + 植入真值"**；真实样本只作演示与人工抽验，**数量不作交付承诺**。这条写进题面是为了防止下游把"5 个样本"包装成"大规模验证"。

## 二、任务要求

> **首期范围限定为五个模块**（M1–M5）；多语言生成、LLM 断言增强、CI 集成、跨会话去重留扩展（§2.6）。全部模块遵循"**未核对字段语义不得落库 / 不得进入生成路径**"的确定性纪律——凡解析某日志字段，必须先以**本机实测样本**核对存在性与语义，核对记录进 [data/README.md](../data/README.md)；未核对字段只能落 `unknown` 或整条跳过，**不得猜测补全**。
> **数值口径一处定义**：episode 打分权重、过滤阈值、验证超时等全部数值，只在 `config/scoring.toml`（或 M1 落定的同名唯一配置文件）定义一次；报告、基准、文档、README 一律引用该处，**不得手写第二份数值表**。本段列出的权重是**题面口径声明**，实现侧唯一权威仍是该配置文件。
> **不写会随实现漂移的硬数字**（测试数 / 文件数 / 体积 / 通过数）；确需数字时以末态回填。

### 模块 M1：双 harness 会话读取器（统一事件流）

- **输入**：
  - Claude Code：`~/.claude/projects/**/*.jsonl`（支持 `--claude-root` / 环境变量覆盖；路径自适应发现，不得硬编码用户名）；
  - Codex：`~/.codex/sessions/**/*.jsonl`（支持 `--codex-root` 覆盖）；
  - 行类型按本机实测处理：Claude 的顶层 `type` 行与 `message.content[]` 内的 `tool_use` / `tool_result`、行级 `toolUseResult`；Codex 的 `session_meta` / `response_item`，其中 `payload` 侧含 `custom_tool_call`（`apply_patch`）与 `function_call`（如 `exec`）。**完整行类型与键枚举不在出题阶段宣称，由 M1 全量聚合后写入 data/README。**
- **输出**：归一化事件流 `Event{ts, kind, tool, path, payload, source, session_id, seq}`，`kind` ∈ {`user_msg`, `assistant_msg`, `tool_call`, `tool_result`, `meta`}；`path` 仅对文件类工具非空；每条事件带**来源行号与原始行偏移**，供后续锚点回溯。
- **格式版本检测**：按键指纹识别日志格式版本（Claude / Codex 各自一个 schema 版本号），不认识的版本**显式报 `unsupported_format` 并列出缺失键**，不得静默产出空事件流；同一日志重复解析结果逐字节一致。
- **确定性纪律**：纯函数、无随机、无网络、无模型；事件顺序 = 文件内物理顺序；无法识别的字段落 `unknown`；**M1 必须先闭环三个 ⬜ 待核对项**（Codex `apply_patch` 载荷内文件路径字段、Claude `MultiEdit` 字段形态、Codex `exec` 失败判定字段语义），核对结论写入 data/README 后，对应字段才允许进入 M2 判定路径。

### 模块 M2：Bug-fix Episode 切分器（确定性规则，无模型）

- **输入**：M1 事件流 + 语义词表（bug / 报错 / 失败 / 崩溃 / 不工作 / 复现 / ERROR / exception / traceback / broken / doesn't work / fail 等，词表在配置文件一处定义）。
- **切分规则（按序、可回溯）**：
  1. **起点**：`user_msg` 命中 bug/失败语义词；
  2. **失败信号**：向后扫描，命中 `tool_result` 含 `FAILED` / `AssertionError` / `Traceback` / `Exit code N`（N≠0）之一；
  3. **修复动作**：失败信号之后出现 `Edit` / `Write` / `apply_patch`（含 Codex patch 容器）；
  4. **终点**：到达"同一测试命令转为通过"的事件，或会话结束（两种终点分别标 `verified_by_run` / `ended_without_pass`）。
- **输出**：`Episode{episode_id, session_id, source, start_ts, end_ts, user_report, failure_evidence[], edits[], test_commands[], score, status}`；`episode_id` = 会话 id + 首次修复事件序号（稳定可复现）。
- **打分（题面口径声明，权威值在配置文件）**：失败信号 **+2**、diff **+3**、测试命令 **+2**、改的是代码而非文档（非 `.md`）**+2**；总分低于阈值（阈值一处定义）的候选丢弃。打分是**确定性规则**，不是 AI 评分。
- **确定性纪律**：同一输入 → 同一 episode 集合与同一排序；边界情形（一个会话多个 bug、先成功后失败、失败后未修复）必须按规则落定并写入测试；不得把"用户仅提问"误切为修复 episode。

### 模块 M3：差分还原器（before/after 重建，不依赖 git）

- **输入**：episode 的编辑事件 + 本机工作区文件（可选）。
- **还原优先级（逐级降级，每级标 `source` 与 `confidence`）**：
  1. Claude `toolUseResult.type == "update"` 的 `structuredPatch` + `originalFile`（before 为全文，最可靠）；
  2. `old_string` / `new_string`：在 `originalFile`、磁盘文件或同会话 `Write.content` 上定位替换，合成 unified diff；`replace_all` 或多处命中且无法唯一定位时标 `unresolved`，**不得任选一处**；
  3. Codex `apply_patch`：解析 `*** Begin Patch` / `*** Update File:` / `*** Add File:` / `*** Delete File:` 与 `@@` 上下文，结合磁盘文件或 patch 上下文行重建 before/after；只能重建局部片段时标 `partial`；
  4. 以上均不可得 → 该文件不进生成路径，episode 记 `unverified: no_before_image`。
- **输出**：`Reconstruction{file, before, after, hunks[], source, confidence}`；多文件 episode 输出列表，逐文件独立置信度。
- **确定性纪律**：**绝不伪造上下文行**；同一日志 + 同一磁盘状态 → 同一 diff；磁盘文件已被后续修改导致无法对齐时，如实降级；不做 git 操作（`git stash` / `git apply` 仅可作为 M5 的可选加速手段，**不是必需依赖**）。

### 模块 M4：pytest 骨架生成器（模板 + AST，不调模型）

- **输入**：M3 的 `Reconstruction` + 目标仓库 + 测试约定探测结果。
- **约定探测**：`tests/` 布局、`pytest.ini` / `pyproject.toml` 的 `[tool.pytest.ini_options]` / `setup.cfg` / `tox.ini`、`conftest.py` 与 fixture 风格、包根与 import 形态；探测失败时用保守默认（`tests/regression/` + 绝对导入），并在 manifest 标注 `assumed_convention`。
- **输出**：`tests/regression/test_<slug>.py`，结构固定为：
  - **docstring**：会话 id、事件时间戳、**原始用户报告原文**、失败信号摘录、修复文件清单（证据锚点可回溯）；
  - **Arrange**：从修改前代码的函数/类签名与 diff 推断最小输入（AST 读取签名；无法构造时留 `# TODO: arrange` 并标 `needs_manual`）；
  - **Act**：调用被修改的函数/类（diff 中被改动的符号优先）；
  - **Assert**：保留 `# TODO: assert` 占位，并附**从 diff 推断的候选断言**（返回值变化、异常类型变化、输出字符串变化），候选断言必须注释标明"候选，需人工确认"。
- **确定性纪律**：纯模板 + AST，**不调用任何模型**；同一 episode → 逐字节相同的骨架（稳定排序、稳定 slug）；目标符号无法识别 → 不生成文件，记 `needs_manual`；生成文件只写入用户仓库的测试目录，**不修改任何源码**。

### 模块 M5：RED 验证器 + 清单（不验证不落盘）

- **输入**：生成的测试文件 + `before` / `after` 内容 + episode 中记录或探测到的测试命令。
- **验证流程（临时副本，不碰用户工作区）**：
  1. 把目标仓库复制到临时目录（或使用隔离的临时工作树），写入 `before` 内容 → 运行新测试，**必须失败（RED）**；
  2. 切到 `after` 内容 → 运行同一测试，**必须通过（GREEN）**；
  3. 任一步不满足 → 标 `unverified`，记录原因（测试未失败 / 修复后仍失败 / 环境不可用 / 超时），**不写入正式测试目录**。
- **输出**：`regression/manifest.json`——每条记录 `episode_id`、`session_id`、`source`、文件与 hunk 摘要、生成测试路径、RED/GREEN 退出码与截断日志摘要、`status ∈ {verified, unverified, needs_manual}`、`reason`、生成器版本与生成时间。
- **CLI 退出码语义**：`0` = 至少一条 verified；`1` = 无 verified（含全部 unverified）；`2` = 用法错误；`3` = 运行依赖缺失（如 pytest 不可用）——**依赖缺失不得退化为"零条结果 + exit 0"**。
- **确定性纪律**：验证在隔离目录进行，**不修改用户源码、不写用户 git 索引**；超时、命令、临时目录策略一处定义；RED/GREEN 结论必须可重复（同环境重跑同结论）。

### 2.6 扩展项（不承诺首期交付）

- **多语言生成**：首期只**识别** `.mjs` / `.ts` 的修复（进 episode 与 manifest），**不生成** JS/TS 测试；后续按语言扩展模板；
- **LLM 断言增强**：用模型补全断言候选——**首期不做**（纯本地、无 GPU/API 依赖是定位的一部分）；
- **CI 集成**：把 `manifest.json` 转为 CI 报告或自动 PR（留扩展）；
- **跨会话去重**：同一修复在多会话重复出现时合并（留扩展）；
- **回滚检测**：识别"修复在后续会话被改回去"，生成反向告警（留扩展）。

## 六、边界与非目标

- **只固化已发生的修复，不生成业务测试**：不替用户"补覆盖率"、不凭空设计新功能测试；只处理会话中真实出现过的"失败 → 修复"链。
- **不修改用户源码**：只写测试目录与临时副本；**绝不改源码、绝不 `git commit`、绝不写用户 git 索引**。
- **不依赖 git**：修改前内容来自日志（`originalFile` / `structuredPatch` / `old_string` / `apply_patch`）；git 仅作为可选的回放加速手段，缺 git 时全链路必须仍可跑。
- **不做 AI 评分**：episode 打分是确定性规则（+2 / +3 / +2 / +2 与阈值），不是模型 judgement；首期不引入任何 LLM。
- **多语言首期只 Python 生成**：`.mjs` / `.ts` 只识别、只进 manifest，不生成测试文件；避免模板与测试框架差异导致的"名义支持"。
- **隐私红线**：会话日志含 **prompt 与代码**——**纯本地、零上传、零遥测、不联网**；真实日志、真实路径清单、真实 session id 一律**不入仓**；生成的测试可能含用户代码，默认只落本地，公开仓库只含合成基准。README 与 `--help` 明写"本工具不发送任何数据"。
- **品牌隔离**：不复制系列其他项目代码；公开文档不提及任何其他项目的业务领域。
- **首期范围限定**：五个模块（M1–M5）；多语言生成、LLM 断言增强、CI 集成、跨会话去重、回滚检测留扩展，不得在首期题面或 README 中承诺为已交付能力。
- **样本量局限如实披露**：严格口径真实样本仅 5 个会话（宽松 29 个），**不足以支撑统计型结论**；真实样本只作演示与人工抽验，正式评测以合成会话植入真值为准。任何"准确率"类表述必须注明分母来源。
- **不承诺跨版本兼容**：会话格式随 agent 版本演进，解析器以"本机实测字段 + 版本指纹"为依据；不认识的新格式显式报错，不得猜测。
