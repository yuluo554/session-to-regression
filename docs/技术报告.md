# 技术报告 · session-to-regression

> 本报告是题面 §三 要求的提交材料之一。**所有数值只引用 `config/scoring.toml`**（权重、阈值、超时、
> 临时目录策略、语料门槛、词表），报告里不复制第二份数值表；行文一律相对路径。
> 配套证据：`plan/verify/README.md`（本地等价校验逐条留档）、`plan/07-交付对标与决策记录.md`（决策与 K 口径）。

---

## 一、问题与定位

coding agent 常"让测试变绿"而不是"让代码变对"，甚至把上周的修复改回去（公开抱怨见 `plan/01`）。
修复是一次性的，回归是永久的。本工具做的事只有一件：**把一次已经发生的修复，固化成一个可复跑的
pytest 测试**，并且**在隔离副本里证明它真的能红灯**。

定位上的三个硬约束（决定了后面所有设计取舍）：

1. **纯本地、零上传**：会话日志含用户的 prompt 与代码，所以不联网、无遥测、不调用任何模型；
2. **不依赖 git**：本机实测 37 个改文件会话里只有 7 个在 git 仓库内——依赖提交历史会让八成会话无法处理；
3. **可复现**：无时钟、无随机、无并发；同一输入双跑逐字节一致（中间层与 CLI 出口**两层**都断言）。

## 二、会话格式归一化

Claude Code（`~/.claude/projects/**/*.jsonl`）与 Codex（`~/.codex/sessions/**/*.jsonl`）是两种形态，
归一化不靠目录名（用户布局会漂），而是**按记录形态分流**：Claude 看顶层 `type`，Codex 看 `payload.type`；
首行形态判不出来就显式报错（`unsupported_format`，并列出缺失键），绝不静默产出空事件流。

三条实测结论直接决定了实现（逐条留档见 `data/README.md` §六）：

| 事实 | 处置 |
|---|---|
| Claude 的 `structuredPatch` 有 305 条带表、其中 **223 条非空**；空表同样出现在纯新建文件上 | before 镜像的判据是**键存在且非空**，不是 `toolUseResult.type == "update"`（后者全量只有 4 条，会把 301 条漏掉） |
| Codex 的结果侧**没有** `exit_code` 键，退出码在 `output` 文本里 | 失败判定只在数值形态上做（`Exit code N` / `Process exited with code N`，且 N≠0）；标记字符串命中不算失败 |
| 同一个逻辑通道可以出现在不同顶层行类型下；`FileChange` 是 Codex 侧唯一带结构化 diff 的通道 | 事件流 IR 按内容形态产出；`FileChange` 作为结果侧事件纳入（**不承诺**与 `apply_patch` 配对——无 `call_id`，按时间序配对属于猜测） |

事件流 IR 只留**引用**：`originalFile` / `structuredPatch` / patch 全文这类逐字节关键的块不进 IR，
只记 `seq`（= 源文件行号）与字节偏移，由还原阶段按需取回原文——避免"截断"毁掉 before 镜像。
`seq` 取源行号而不是数组下标，因为它可被日志独立复算（紧凑下标会随解析过滤漂移）。

## 三、episode 切分口径

切分是**确定性状态机**（无模型、可解释、可复现），四步按序：

1. **起点**：用户消息命中语义词表（`vocabulary.bug_terms`）；
2. **失败信号**：向后扫到 `tool_result` 命中失败信号（`vocabulary.failure_signals`）；
3. **修复动作**：失败信号之后出现文件写类工具；
4. **终点**：**同一条**测试命令转为通过（按 `call_id`/`tool_use_id` 配对，不按时间序猜）→ `verified_by_run`；
   否则会话结束 → `ended_without_pass`。

打分只用于过滤噪声，权重与阈值只在口径文件里：失败信号 +2、可还原 diff +3、出现测试命令 +2、
改的是代码而非文档 +2，低于 `scoring.threshold.min_score` 的候选进 `filtered[]` 并带原因。
「只改文档」是**独立丢弃规则**（不靠阈值碰巧过滤）。词表与标记一律运行时从口径文件取，
源码里连词面都不复述（有守门测试）。

## 四、还原降级策略（before/after 重建）

优先级逐级降级，每级标 `source` 与 `confidence`：

1. Claude `originalFile`（修改前全文）+ **非空** `structuredPatch` → `high`；hunk 先按行号对齐，
   对不上再按内容唯一定位；
2. Claude `old_string`/`new_string` 在 before 基线上定位替换 → 基线按 `originalFile` → 磁盘
   （**仅显式 `--repo`**）→ 同会话更早的 `Write.content` 取第一个可用者；
3. Codex 首选 `FileChange.unified_diff`（结构化、带路径行号），`*** Begin Patch` 文本解析作兜底；
4. 都不可得 → 该文件不进生成路径，episode 记 `no_before_image`（新建文件的 `after` 仍取自日志正文——
   那是事实，不因缺 before 就丢掉）。

**四态不折叠**：`ok`（before/after 齐）/ `partial`（只有片段，`before`/`after` 为 null，**绝不伪造上下文行**）/
`unresolved`（有多处候选、无法唯一定位，**不得任选一处**）/ `no_before_image`。
置信度由 **before 镜像的来源**决定，不由结果好坏决定：日志内全文 `high`、磁盘工作区 `medium`、
片段 `low`、取不到 `none`。磁盘对齐是**显式开关**：不给 `--repo` 就不碰工作区，给了也只读。

## 五、模板生成与候选断言的推理

生成是**纯模板 + AST**，零模型：

* **docstring 证据锚点**：会话 id、事件时间戳、**原始用户报告原文**、失败信号摘录、修复文件清单——
  五类锚点都可在日志里复算（原始报告逐字入文，不做转义，冲突时退化成注释块）；
* **Arrangement**：AST 读**修改前**的签名，逐形参绑最小输入（含 `self`/`cls` 的接收者构造，
  签名含可变参数则判定"最小调用构造不出"）；
* **Act**：调用被改动行所属的**最内层**定义（类内方法优先于类）；
* **Assert**：占位注释 + **候选断言**。

**候选断言只认一种可证伪形态**：改动的新行是 `return <expr> if <cond> else <alt>`、`<cond>` 恰是被调
符号的形参名、`<alt>` 是字面量。此时把该形参绑成与 `<alt>` 同型的**假值**，于是修复前抛错（红）、
修复后返回 `<alt>`（绿）——`assert result == <alt>` 天生可证伪。这是唯一能**保证**"能红"的形态，
所以推不出来就不猜：仍产出骨架（三段 + 锚点），但标 `needs_manual` 并给原因码
（`assert_not_derivable` / `probe_not_derivable` / `symbol_not_identified` / `not_python` /
`before_unparsable` / `changed_lines_unknown`）。每条候选断言都带口径文件里的"需人工确认"标注。

两条纪律：**宁缺勿造**（没有修改前全文就没有"修改前的签名"——硬造出来的只是看起来像测试的东西）、
**只写测试目录**（生成前后目标仓库源码树逐文件哈希不变）。

## 六、RED/GREEN 隔离验证与 manifest

写完骨架只是候选，**跑得动才算证据**。验证流程：

1. 目标仓库 → 临时目录副本（前缀取自口径文件 `[verify].tmpdir_prefix`；版本库与缓存目录不复制）；
2. 把日志还原出的 `before` 覆盖进副本 → 跑新测试 → **必须失败（RED）**；
3. 换成 `after` → 跑同一测试 → **必须通过（GREEN）**；
4. 任一步不满足 → `unverified` + 原因，**不写进正式测试目录**。

判定只看退出码语义（`0` = 通过、`1` = 有测试失败；其余码属环境/用法问题，不当作判定依据），
不看输出文本。四类 `unverified` 原因：`red_not_failed`（测试未失败）、`green_not_passed`（修复后仍失败）、
`environment_unavailable`（环境不可用，含"日志里的路径在目标仓库里定位不到"）、`timeout`。

**三态不折叠**：`verified` / `unverified` / `needs_manual`。特别地，生成层标了 `needs_manual` 的骨架
（没有活动断言）**照样跑两次**——它会在修复前"不失败"，于是结论是 `unverified` + `red_not_failed`：
**"测试没失败"与"测试通过了"是两件事**，把它当 verified 是最容易发生的一种自欺。
只有 `verified` 的测试才写进目标仓库的测试目录（`unverified` / `needs_manual` 只进 manifest）。

`regression/manifest.json` 是给别人复核的那份证据：逐 episode 记会话 id / 来源 / 生成时间 / 生成器版本 /
改到的文件与 hunk 摘要 / 生成层结论与原因 / 测试路径与是否落盘 / 结论与原因 / RED-GREEN 退出码与摘录；
`skipped[]` / `failed[]` 让批内隔离（读不了的文件）可见；覆盖度门槛自基准 manifest 下发。

**生成时间不用时钟**：取会话日志自身的 `end_ts`（可复算）。日志摘录只保留 `E` / `FAILED` / `ERROR`
前缀的行——pytest 的头部含平台、版本、耗时、临时目录，直接摘录会让 manifest 每次都不一样，
"同输入同产物"这条承诺就会在这份最该被复核的产物上失效。

## 七、隐私设计

四层防线（第 ① 层已落地，其余三层是发布期审计项）：

1. **源码层**：可发起网络调用的顶层导入（socket/http/urllib/...）出现即红；源码文本不得含本机盘符/
   家目录形态路径；词表不复述；
2. **语料层**：入仓的只有**合成会话**（假项目名/假路径/假 session id，白名单见 `data/README.md` §三），
   生成后逐条自检"任何绝对路径不在白名单前缀内即报错"；真实日志、真实路径清单、真实 session id
   **一律不入仓**（`.gitignore` 另设数据目录屏蔽规则）；
3. **运行层**：不联网、无遥测；`--repo` 是磁盘读取的**显式开关**，不给就不碰工作区；
   RED/GREEN 在**临时副本**里跑，用户仓库不落任何中间件（连 pytest 缓存都在副本里）；
4. **发布层**（待 M6）：发布产物扫描 + socket 拦截动态验证 + 加载面静态检查。

## 八、验证与基准（本项目自己的"考卷"）

* **合成语料 + 程序化植入真值**：10 类样本（正常修复链 / 未观察到通过 / 一会话多 bug / 无失败信号 /
  只改文档 / 多重定位 / 纯新建文件 / 结构化补丁 / 磁盘基线对不上 / 未知格式），语料/T真值/磁盘基线
  夹具的 sha256 进台账，`tools/gen_bench.py --check` 复算位级一致（冻结物被手改即红）；
* **四层真对账**：事件层（计数/工具/路径/退出码）、episode 层（该切/不该切 + 丢弃原因）、
  还原层（逐文件逐字段 before/after/来源/置信度）、生成层（骨架数 / 逐 episode 结论 / 候选断言条数 /
  锚点）、**验证层**（逐 episode 三态结论 + RED/GREEN 退出码——验证真的跑过两次，不是声明）；
* **双边门**：既守检出率（≥ 门檻且逐样本点名）也守误报 0；完整性门（台账/在位/覆盖度）看全量语料，
  判定门看 `--only` 选中项；
* **九个探活**：向对账路径注入已知缺陷并要求基准报未达标（含"把 before 换成 after"、
  "把候选断言整段丢掉"、"把 unverified 折叠成 verified"）——探活自己变成假门也会被抓住；
* **变异验证**：每个新守门都被"故意弄坏"一次，弄不红即视为假门当场重写；
* **双解释器**：Python 3.8（下限）与 3.12 各跑全量测试；离线冒烟覆盖每条已交付命令的
  `s2r` 与 `python -m s2r` 两种形态。

## 九、已知限制（不包装）

首期只固化**已发生**的修复、只生成 Python 测试、只认一种可证伪的候选断言形态；
验证要求目标仓库里存在该 episode 改到的文件（否则如实记环境不可用，**绝不替用户新建文件**）；
一个目标仓库 = 一份工作区状态，所以 `run --target` 的核验面是"当前状态下能验证几条"；
Codex 侧没有 before 全文，缺磁盘基线就只能落 `partial`、也就没有可验证的骨架；
样本量如实披露（严格口径真实端到端样本 5 个会话），因此评测主体是合成基准。
